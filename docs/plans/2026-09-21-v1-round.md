## 查出来的事实（都有证据，不是推测）

### 旗标面

- `src/env.ts` 共 **498** 个键，其中布尔旗标 **221** 个，生产实际开着 **191** 个。
- **9 个死旗标**：`.env` 开着或默认开着，而 `src/` + `scripts/` + `packages/` 里
  `env().FLAG` / 解构 / `process.env.FLAG` 三种读法全无命中。
  `PROACTIVE_PRESSURE_ENABLED` `SCHEDULE_LLM_WAKE` `GOAL_LONG_TERM_ENABLED`
  `CORE_BLACKBOARD_ENABLED` `AGENT_PROGRESS_PING_ENABLED`（`.env=true`）、
  `REPLY_MODE_ENABLED` `REPLY_ACK_THEN_EXPAND_ENABLED`
  `TASK_PROGRESS_CODEACT_ENABLED` `TASK_PROGRESS_RESEARCH_ENABLED`（默认 true）。
  最坑的是 `GOAL_LONG_TERM_ENABLED`：注释说“可关”，而 `goals.ts` 用的是硬编码常量
  `GOAL_LONG_TERM_STALE_AFTER_SEC = 30 天`。
- **4 个假开关**：只被测试 mock，`src/` 不读。`CORE_BLACKBOARD_ENABLED` 是典型——
  `src/core/blackboard/` 有一整套实现，导入方（`agent/cognitive-workspace`、
  `agency-intent-adapter`、`core/promote`、`core/permission/gate`）全是**无条件跑**的。
  测试把它设成 false 以为关掉了黑板，其实什么都没验证。
- 判定方法必须三种读法都算，否则会把活旗标误判成死的（第一版只 grep `env().FLAG`，
  差点误判 5 个）。

### 频率（用户投诉“日常过高”）

近 3 天 3,008 次群发送：小时窗 p50=6 / p90=26 / p99=63 / **max=107**；
5 分钟窗 p50=2 / p90=8 / **max=20**；最忙四群平均 14.7–19.4 条/小时。

两个病因，都是 bug 不是设计：

1. **发送预算每段归零**。executor 每段重建 `createHostApi`，`textSent` 归零，
   `maxTextSends=6` 其实是“每段 6 条 × 最多 10 段 = 60 条”。
   `semantic-dup.ts` 的注释早就写着“上限=6 —— 恰好就是 6，等于没拦”。
   证据：投递数分布恰好在 6 条处跳变（31 → 51），最差一个任务 46 秒 12 条。
2. **被叫到的回复一点间隔都没有**。最小间隔只拦主动发言，而生产流量几乎全在
   “被叫到”那条路上（2,702 次 `host sendText`：1,356 显式 `replyTo` + 1,340 只有任务默认锚点）。

另外：`TRENCH_BURST_MAX/ACTIVE` 原值 150/100 经 `envelope-backtest` 回测是**装饰性**的
（拦 0.0%）。已按实测改成 30/20（拦 11.9%，基本全是 p99 以上的失控小时）。

### 身份认知

- `runFeedbackAggregate`（每小时 cron，自我笔记的唯一写入方）只读 `feedback_events`：
  **一共 4 行**。而 `reply_outcomes` 有 **12,752 行**、带 signal，从没被自我认知读过。
- 结果：`self_model_notes` 最新一条停在 **2026-09-11**，之后十天模型没看到过关于自己的新事实。
- 近 3 天 1,208 条回复结果里 **738 条是 `ignored_5_msgs`**（“我连发 5 条没人理”），
  `user_replied` 只有 85。过度发言的代价全在这张表里。
- 已改成也聚合 `reply_outcomes`，加去重（`saveSelfNotes` 是裸 INSERT 无唯一约束，
  原实现两条文案写死，持续偏负会每小时插一条一样的）和最小样本 20。

### 节假日 / 作息（本来就有，缺的是数据）

- 节日提示在跑：`src/shared/beijing-time.ts` 查表（公历+农历+节气，到 2027），

  10/10(六) 补班日被当成自由周末。已按国办发明电〔2025〕7 号登记 33 + 6 行。

### 架构（**还没动**，下一轮的主菜）

- Core v2 **在跑**，不是死的：`CORE_V2_CHAT_IDS` 空 = **全量生效**（与 TURN_ACTOR 一致），
  log 里 757 次 `core shadow compare`。我一度以为它没跑，是看 log 才纠正的。
  但 `CORE_BELIEF_VIEW_ENABLED` / `CORE_BLACKBOARD_ENABLED` 这两个“闸”确实没人读。
- 两条 pipeline 并存：Meta+Subagent（`META_SUBAGENT_ENABLED=true`，生产主路径）和
  `processPipeline`（heart 分支）。Meta 路径**绕过** `processPipeline`，
  这就是为什么 bot 分类器/denoise 曾经在主路径上从未运行。
- `src/core/` 有 beliefs / blackboard / drives / l2 / permission / promote / agenda / skills
  一整套，其中 belief view 和 blackboard 无条件跑、旗标是摆设。

## 顺带发现但**本轮没修**的

1. **ASI rubric 列基本是常数**：`reply_outcomes` 的
   `(rubric_social_presence, warmth, competence, appropriateness, uncanny_risk, asi_final)`
   2,070 行一模一样 `(0.5, 0.5, 0.5, 0.5, 0.2, 77.0)`，560 行 `(…, 99.0)`，
   125 行 `(…, 13.0)`，只有约 20 行是真测量值。**看着有数、其实没信息**。
2. `REPLY_MODE_ENABLED` / `REPLY_ACK_THEN_EXPAND_ENABLED` 那一整个“回复形态与安全分段”
   特性既没开也没实现。
3. `xxb:trench:antiad:*` 的 scan 会捞到 `fp:` / `win:` 子键（hash/zset），
   用 `redis-cli get` 探活会误报 WRONGTYPE。

## 下一轮该做的（按依赖排序）

1. **老架构替换**：先按旗标审计把 9 个死旗标 + 4 个假开关处理掉（删 flag 或真接线），
   这是“替换”的前置——不知道什么在跑就没法删。
2. **Core v2 的两个假开关**：要么真接线（belief view / blackboard 各自由 flag 门控），
   要么删 flag。无条件跑的子系统 + 一个关不掉的开关是最难维护的组合。
3. **ASI rubric**：查清那 2,070 行常数是哪来的（是占位填充还是评分全落在默认值），
   要么修要么把那几列撤掉——假的度量比没有度量更坏。
4. **新架构扩展性**：smart-group 的 newcomer bug 已修（无数据者按池内延迟中位数归位）；
   下一个同类问题是 498 个 env 键的发现性——加一个功能要翻 1700 行 schema。
   考虑按子系统拆 `env.ts`（core / trench / meta / pipeline / tracking …）。
5. **前置功能**：用户点名 `time gate`。现有 `TIMING_*` 一族 12 个旗标，
   其中 `TIMING_GATE_PRECHECK_ENABLED` / `TIMING_GATE_HISTORY_ENABLED` 等是“LLM 之前的
   确定性层”——这一族值得单列review，因为它们正是“bot 该不该现在说话”的前置判断。
