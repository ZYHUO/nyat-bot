### 频率（用户投诉“日常过高”）

近 3 天 3,008 次群发送：小时窗 p50=6 / p90=26 / p99=63 / **max=107**；
5 分钟窗 p50=2 / p90=8 / **max=20**；最忙四群平均 14.7–19.4 条/小时。

两个病因，都是 bug 不是设计：

1. **发送预算每段归零**。executor 每段重建 `createHostApi`，`textSent` 归零，
   `maxTextSends=6` 其实是“每段 6 条 × 最多 10 段 = 60 条”。
   `semantic-dup.ts` 的注释早就写着“上限=6 —— 恰好就是 6，等于没拦”。
   证据：投递数分布恰好在 6 条处跳变（31 → 51），最差一个任务 46 秒 12 条。
2. **被叫到的回复一点间隔都没有**。最小间隔只拦主动发言，而生产流量几乎全在
   “被叫到”那条路上（2,702 次 `host sendText`：1,356 显式 `replyTo` + 1,340 只有任务默认锚点）。

另外：`TRENCH_BURST_MAX/ACTIVE` 原值 150/100 经 `envelope-backtest` 回测是**装饰性**的
（拦 0.0%）。已按实测改成 30/20（拦 11.9%，基本全是 p99 以上的失控小时）。

## 第二轮查出来的事实

### 视频（用户新指出）

"stepfun 模型实际上是可以视频 5min 以内输入的，vision 应该不止可以识别图片还可以识别视频"。

`multimodal.ts` 里只有一行 `[视频：用户发送了一段视频]` + "description not supported yet"。
**那个判断曾经是对的，现在过期了**——实测 step-5-preview 吃 base64 `video_url`，
6 秒测试视频准确描述了内容（彩色条纹/彩虹斜线/移动方块/左上角计时器）。

四个坑，三个是陷阱：

1. **不能蹭 vision 链**。同一个 `video_url` part 发给 step-3.7-flash 返回 **200 但
   content 为空**——token 全烧在 reasoning 上，`finish_reason=length`。
   "返回 200"不等于"看得懂"。所以加了 `AI_PROVIDER_X_VIDEO` 能力声明，
   smart-group 的 video profile 只收显式声明 true 的 label。
   方向性与 vision 相反是故意的：vision 没声明照发，video 没声明就不要。
2. **max_tokens 必须给够**（2000）。
3. **时长上限在下载之前判**（300s）。Telegram bot 下载上限 20MB（代码 10MB），
   5 分钟视频几乎必然超——现实里能描述的是短视频。
4. **绝不把 Telegram file URL 喂供应商**：那个 URL 里带着 bot token。

### 挖出的静默 bug（比功能本身重要）

全接完之后端到端跑出来是 **"我没看到你说的视频呀"**，而 prompt token 数也对得上。
原因在 `callModel`：`apiFormat === 'claude'` 时 content parts 被映射成
`p.type === 'text' ? p.text : ''` —— **图片、音频、视频全被换成空字符串**。
没有报错，token 数也对（只有文字那部分）。

修法：带媒体时绕过 claude 分支走 OpenAI 兼容裸路径（StepFun 的 `/step_plan/v1`
同时提供 `/messages` 和 `/chat/completions`，后者收 `video_url`；
Anthropic 原生 video block 在那个端点上回 400）。这条**顺带也修好了
claude-format label 的图片丢弃**。

### time gate（用户点名的"前置功能"）

TIMING_* 13 + TURN_* 17 个旗标，生产开 7 个。Meta 主路径**确实**跑 gate
（`src/meta/timing-adapter.ts` → `runTimingGate`）——我一开始猜"绕过
processPipeline 所以没跑"，看代码才纠正。

日志里它在真干活：333 no_action / 292 defer / 170 talk-value / 125 decision /
10 precheck / 620 dispatch gate suppressed。

**但 199 次 "gate parse failed"**（占 324 次的 61%）。env.ts 注释早就把这记成
"实测依据"放了很久。查下去发现 `rawSnippet` 全是空——不是解析不了，是**模型没输出**。

根因：调用点写死 `maxTokens: 200`，而 `.env` 把 `TIMING_GATE_USAGE` 设成
`reflection` → stepfun = step-3.7-flash（reasoning 模型，思维链计入 completion）。
实测同一 prompt：200 → content 空；800/2000 → 合法 JSON。
思维链吃光 200 token，JSON 没机会输出，然后 fail-closed 沉默——
**看起来像"gate 判了不说话"，实际是"gate 被截断了"**。
`labels.ts` 里 judge usage 的注释早就警告过这事，gate 是唯一还写死 200 的调用点。

已加 `TIMING_GATE_MAX_TOKENS`（默认 1200，实测合法 JSON 只需 ~260 token）。

### provider 池：33 个 label 只有 5 个成功过

### ASI rubric：假度量

`reply_outcomes` 的 rubric 五列基本是常数：2070 行一模一样

# 第五轮：新增前置功能 + provider 池病因定位

## 新增前置功能：心流 LLM 失败时的保句闸

翻日志发现一个数字不对：`heart LLM failed, fail-closed pass` **1867 次**，
`Heart decision` 7443 次 —— **25% 的心流裁决是 LLM 调用失败**。

失败原因分解：
  1194  All labels exhausted（64%，整条 fallback 链死透）
   169  Content rejected
   162+32  timeout
    60  all accounts unavailable (cooling/disabled)
    56  ECONNRESET · 38 TLS 断 · 73 rate limited · 18 connect timeout

旧行为一律 `pass` = 消息被永久丢弃。对没人叫 bot 的群聊消息没毛病，但对**直接
叫到 bot** 的那句是另一回事：有人 @ 了本喵问一件事，因为线路故障，这句话就此
消失，对方永远等不到回复。这和"无视直接提问是另一种失败"是同一条原则，
只是失败方从模型变成了线路。

`HEART_LLM_FAIL_KEEP_ADDRESSED`（默认开）：LLM 判不了 + 被直接叫到 → `wait`
（走既有 wait-anchor 机制稍后重评），不 `pass`；没被叫到仍旧 `pass`（避免线路
故障时把整群闲聊都排成重试）。

wait 这条路两个消费方都已实现（heart.ts:313 和 meta/heart-adapter.ts:222），
所以保句是真保句，不是换个姿势丢弃。

## provider 池病因定位（比"端口写错"更具体）

"All labels exhausted" 占心流失败 64%，而它和 provider 池健康状况直接相关：
heart 走 judge usage → label `stepfun`，backups 里只有 `stepfunjudge` 健康，
其余 7 个是死 provider。**链的有效深度是 2。**

另外查到 `.env.example`（git 里的规范配置）明确写着本地 relay 是
`http://127.0.0.1:8317/v1`，而生产 `.env` 写的是 `3000` —— 这是**配置漂移**，
不是"未知上游"。但 model 名那一层仍然是决策（relay 217 个模型里约一半有对应、
一半没有，gpt-5.x / minimax / mimo / hy 全无），所以仍旧没有擅自重映射。

## provider 池：本地 relay 探不通，所以"改端口"不是解法

第五轮本来想给"23 个死 provider"找一个不需要人拍板的解法。线索是
`.env.example`（git 里的规范配置）明确写着本地 relay 是 `127.0.0.1:8317`，
而生产 `.env` 写 `3000` —— 看着像单纯的配置漂移。

**实测把这条线索否掉了。** 拿 relay 自己的 key 打它自己 catalog 里的 11 个候选模型：

| 模型 | 结果 |
|---|---|
| claude-sonnet-4.5 | HTTP 503 |
| claude-haiku-4.5 | HTTP 503 |
| grok-4-1-fast-reasoning | 45s 超时 |
| grok-4-0709 | 45s 超时 |
| grok-3 | 45s 超时 |
| kimi-k2.5 | HTTP 500 |
| glm-4.7-flash | HTTP 500 |
| glm-5 | HTTP 400 |
| qwen3.6-plus | HTTP 400 |
| deepseek-r1 | HTTP 400 |
| Gemini 3.1 Flash Lite Preview | 45s 超时 |

**11 个全挂。** 所以把 23 个 provider 改指 8317 只是把错误从

这反过来解释了心流失败的头号原因：heart 走 judge usage → `stepfun`，
backups 里只有 `stepfunjudge` 健康，其余 7 个是死 provider ——

（stepfun / stepfunjudge / stepfunthink / stepfunvision / spark13），
要扩池只能加**远程** provider。这一步仍然要人决定加哪些。

# 第六轮：心流失败归因到链，再归因到账号

## 1. 头号失败原因不是超时限流，是思维链吃光 max_tokens

第五轮定位到"心流 LLM 失败占 25%，64% 是 All labels exhausted"。这轮往下挖一层，
看**每个 label 各自怎么失败的**：

  1481  stepfunthink     Empty response
   685  stepfunvision    Empty response
   583  stepfun          Empty response
   133  stepfunjudge     Empty response
   253  wbdsv41free      Empty response from SDK
   602  spark13          timeout
   …

**`Empty response` 2882 次，压倒性头号原因。**

根因：StepFun 那几个是 reasoning 模型，`reasoning_content` 计入 `max_tokens`。
思维链吃光额度时响应带 `stop_reason: 'max_tokens'` 回来，**一个 text block 都没有**。
`callClaude` 里有段注释说明这个现象，然后**故意**返回空字符串交给 fallback——
而 fallback 是同账号的另一个 label，撞同一个天花板，一次全灭。

先探针验"长 prompt + 4096 会不会空"——没复现。所以没继续猜，改成
**分开两种形状 + 把为什么空记进日志**：

  stop_reason=max_tokens + 无 text → 截断 → 加额重试一次（翻倍，上界 32k）
  stop_reason=end_turn  + 无 text → 模型真没话说 → 不重试

只对截断重试（审查/超时/限流重试只会翻倍延迟）。空正文时现在记
stopReason / blocks / outputTokens / maxTokens——此前 2882 次失败一点可诊断信息都没有。

## 2. 链的上游去重

同一个故障的另一面：健康 label 里四个共用同一个 endpoint + key，按延迟排序连排，
账号级限流一来四个同时死，链上瞬间一个不剩；真正独立的 step5 / spark13 被挤出名額。

`SMART_GROUP_DIVERSIFY_UPSTREAM`（默认开）：每个 (endpoint, apiKey) 只先取最快的
一个填前段，剩余名額才按分数补。5 名額的链开头从 2 个账号变成 3 个。

## 3. 一次断言修正（记下来是因为它是个真陷阱）

第一版测试断言"链里同账号 label 只出现一次"。错了——补位步骤会合法地把同账号的
加到尾部。真正该锁的性质是**前几个是不同上游**，不是"同账号只出现一次"。
写成后者会让一个正确的实现被测失败。

# 第九十七轮：round 96 的假设也错了——两个新 provider 很稳，只是慢

round 96 我在文档里写"新接的两个 provider 都不稳"，并开出处方：
"摘之前各打 20 次看真实稳定率——round 84 我各打了 1 次就下结论，这次不能重犯。"

照做了。20 次/个：

  amdqwen   ok=20/20   中位延迟  5913ms   错误 {}
  spark13   ok=19/20   中位延迟 19757ms   错误 {fetch failed: 1}

## 结论反转

**两个 provider 都稳**（100% / 95%）。问题不是稳定性，是**慢**。

`spark13` 中位 19.8 秒——而调用方给的上限是：

  topic-scan      maxTimeoutMs 12000
  reflection      maxTimeoutMs 20000
  syco-audit      maxTimeoutMs 12000
  post-task       maxTimeoutMs 10000

**调用方的 cap 一律小于 provider 的中位延迟**，所以 spark13 一上就超时。
日志里那些 `spark13 timeout` 不是它坏，是**我们只肯等它十几秒**。

`AI_PROVIDER_SPARK13_TIMEOUT=60000` 配了 60 秒也没用——`callModel` 取的是
`Math.min(usage.timeout, options.maxTimeoutMs)`，调用方的值赢。

## 对 round 95 那个"五项全差"的最终解释

链 `stepfunvision → step5 → amdqwen → spark13` 是按延迟排的，顺序没错。
但第一位 `stepfunvision` 撞并发限额失败后，要一路退到第四位——**每一跳都烧一个
`maxTimeoutMs`**，三个跳就是 36-60 秒，而整批还有 tick 预算挡着。

所以"失败变多"的机理是：**链变长了**（round 84 加了两个慢 label），
而每一跳都贵。不是闸的错，也不是 provider 的错，是**我把慢 label 加进了
一条用紧超时的链**。

## 下一轮

两个选择，都要先承认代价：
  a. 把 `spark13` 从 judge/summarize/reflection 链里摘掉（它 19.8s 中位，
     对这些 12s 上限的调用方没有用处）
  b. 把这些调用方的 `maxTimeoutMs` 提到 25s+——但 tick 预算和用户体验都不答应

倾向 (a)：**一个 provider 对该调用方没有用处，就不该占链位**。
链位的价值在于"第一位失败时能接得住"，而接住要花 20 秒等于没接住。

## 为什么 peer-reaction 那个不算病

它是"每 10 分钟最多 N 次"的固定窗口，键按 (chat, peer) 分但不按时间分。
固定窗口的已知特性是边界处可突发 2×，而 `FATIGUE_MAX` 是个防对喷的粗闸
不是精确限流器，且窗口只有 10 分钟。

和 round 103 那个的区别在**量级**：那个是 24h 窗口 + 阈值 3，
可以让一个四天没出问题的 model 被熔断；这个是 10 分钟窗口，
最坏情况是 20 分钟内多喷一倍。后者不值得为它改滑动窗口。

## 结论

这一类病（**不会过期的计数参与实时判断**）在全库有**三处实例**，
分别落在 round 87 / 102 / 103，都已修且有测试或实测覆盖。

（这是这个会话里"同因 elsewhere"第三次兑现，也是第一次**搜完给出否定结论**——

## 一个本来想问"要不要降到 3"的问题，答案是不用

我想把零成功档从 5 降到 3（坏替补攒样本太慢）。查了才发现：

**熔断器的阈值就是 3**（`DEFAULT_FAILURE_THRESHOLD = 3`）。

也就是说"连续 3 次失败"这件事**熔断器已经在管**——失败 3 次就冷却，
那段时间里它不会被调用。所以：

  · 连续失败 → 熔断器管（3 次，短期冷却）
  · 从不成功 → 这个门槛管（5 次零成功，长期不进链）

两者的阈值 3 和 5 是**故意错开**的：如果都是 3，这个门槛就完全是熔断器的复制品；
如果都是 5，中间那段（3-4 次失败）没人管。**5 是"比熔断器多给两次机会"的那个数。**

降到最后我会把一个有分工的两个机制变成一个。

包括它们的慢。** 而"慢"在这里不是缺陷——是"多给两次机会"的代价。

# 第一百一十二轮：兜底不是坏了——它按构造必然是空转，而真正的保护在更早

round 111 问"为什么 autoDispatchL0 跑了 246 次产出 0"。这轮读调用点，答案在第一行。

## 根因：L0 在 Meta LLM **之前**就已经派发完了

`src/meta/session.ts:797-810`：

  const earlyL0 = workAttention.filter(
    (a) => (a.layer === 'L0' || a.reason.includes('heart:')) && ...);
  if (earlyL0.length > 0) {
    const busy = await autoDispatchL0(earlyL0, dispatchedChatIds, workMaps);
    ...
  }
  const metaSkipChats = new Set([...dispatchedChatIds, ...earlyBusy]);
  const metaAttention = filterAttentionForMetaLlm(workAttention, metaSkipChats);

**L0（含 DM / @ / reply-to-bot / nickname direct）在调 Meta LLM 之前就派发出去了。**
等 LLM 在 952 行失败、catch 里再调 `autoDispatchL0(workAttention, ...)` 时，
那些 chat 已经在 `dispatchedChatIds` 里，被 `!skipChatIds?.has(a.chatId)` 滤掉。

**所以 catch 里那次调用按构造必然是空转。** 它不是坏了，是重复的第二道——
而第一道在 40 行之前已经跑完。

## 生产读数（支持这个解释）

  Meta dispatch.taskToGroup     2023 次
  CodeAct task start            2558 次
  Meta LLM failed                246 次

**派发量是失败量的 8 倍。** 被叫到的消息走的是 earlyL0 那条路，不等 Meta LLM。

## 修正 round 110/111 的结论

我前两轮写"两层保护，一层接不到，一层空转"——**后半句错了**。
兜底确实空转，但空转是因为**不需要它**：真正的保护在更早的位置，
而且它在生产里跑了 2023 次。

round 110 的保句闸结论不变（它确实 structurally 不可达），但它要保护的事件
**已经被 earlyL0 接住了**。所以那不是缺口，是重复设计。

## 这一轮的性质

**两轮追一个"0"，追出来答案是"这个 0 是正确的"。**

而错的根源在 round 111：我看到"兜底产出 0"就认定兜底失效，
**没先问"这个兜底在时序上还有必要吗"**。catch 块里的第二道防线，
天生只在该失败发生在第一道之后才有意义——而这里的失败点确实在第一道之后。

# 第一百一十五轮：并发闸等太久了——round 95 的假设①这轮被证实

等 4.4 秒是烧掉半个超时预算 + 拖慢整批 tick。限额仍然守（round 81 实测
撞限额 529 次/天），只是把"不可观测的四秒半停顿"换成"可观测的一次 429"。

## 顺带：合龙检查抓到一个真信号

  stepfunvision(stepfun)  dsv4exp(7864)  stepfunthink(stepfun)

**第 1 和第 3 是同一个上游。**

成因是 round 102/105 的两道闸把池子收窄了：零成功快档排掉了
scnet / grok45med / grok43vision / kimi / wbdsv41free，延迟上限排掉 spark13 / amdqwen。

# 第一百一十七轮：并发上限 6 → 7——我们为了不撞 8 的限额，自愿只跑 75%

round 115 实测：上限 6 时排队 328 次、**均等 4385ms**。
而我们明明知道 StepFun 的限额是 8。

## 账

为了不撞 8 的限额，我们自愿只跑 6（75% 容量），
然后**每次多等 4.4 秒**——而调用方的 `maxTimeoutMs` 只有 10-20s。
等完再跑大概率超时。

**省下的限额全赔在超时里。**

## 调到 7

比 StepFun 的 8 少 1（给 provider 自己的内部并发留一点），但不再自缚。

这个改动和 round 115 的排队上限是配套的：那个改动已经把"等太久"换成
"可观测的一次 429"，那么上限就该**贴着 provider 的真实限额走**，
而不是留一个我们付不起的余量。

现在两个代价明确可比：
  超发 = 一次 429 + 60s 冷却
  等待 = 半个超时预算 + 拖慢整批 tick
前者小得多。

## 部署后 3 分钟（样本极小，只作方向）

  llm_concurrency_waits_total        1 次   （round 115 是 328 次）
  llm_concurrency_wait_ms_total    561ms   （那一次等了 561ms，在 1500ms 上限内）

## 但我不宣布成功

3 分钟、2 ok / 6 err，**这个样本什么都不能证明**。
而且 6 次失败里有可能就包含因上限提高而新增的 429——
那正是我换来的东西，得看它是不是比省下的等待更便宜。

下一轮（有 10 分钟以上 awake 数据时）该同时看三个数：
  排队次数、wait_timeout 次数、429/并发超限次数。

  1. **协议内部件**（runtime.* 19 个）——不该算"广告给模型的能力"，
     是 CodeAct 的骨架。把它们从 79 里剔掉，广告面是 60 个。
  2. **模型自己不用**（memory.search / sendPoll / sendPhoto…）——模型没选择调它们。
     这可能是好事（用不到），也可能是模型不知道它们存在。**分不清，因为没记"为什么没调"。**
  3. **广告了但是坏的**（web.search / pixiv.search / linuxsb.topic）——这三个是确定的缺口。

## 和 round 78 的关系

round 78 我读过同一份广告清单，当时核对的是"能力有没有"，
结论是投票/提醒都有（sendPoll + goals.add）。**没核对"调起来通不通"。**

这一轮补上那一半，而补出来的结果是：**60 个广告的能力里，能确认打通的只有 11 个。**

这不是说那 49 个都坏——是说**我们不知道**。而 round 122-124 那次搜索事故说明：
"不知道"的代价可以很大（模型会诚实地说"我没搜到"，而那是个谎）。

## 下一轮

给 host-api 的工具调用加统一的成败计数（像 llm_requests_total 那样），
让"广告了但从未成功调用过"变成一个可查的数字，而不是要 grep 日志才知道。
这是 round 26（失败率要三个出口都数）在工具层的同一次补课。

# 第一百二十七轮：计数器接错了层——8 个任务跑完，一条都没记

round 126 加了工具调用计数。这轮查数据：**部署后 8 个 CodeAct task 跑完，
`host_tool_calls_total` 一条都没有。**

## 病因：Proxy 只包了顶层，而工具在第二层

api 的形状是

  { telegram: { sendText, sendPoll, ... }, memory: { search, ... }, ... }

我的 Proxy 在 `get('telegram')` 时拿到的是**对象不是函数**，原样返回。
于是 `host.telegram.sendText()` 完全绕过计数。

**计数器挂在一个永远不被当作函数访问的键上。**

## 改成递归 → 炸了 7 个测试

递归 Proxy 能让它工作（`get('telegram')` 返回包过的对象），但

  tests/unit/subagent/unviewed-results.test.ts 等 4 个文件、7 个测试红

最典型的一个：「调了 web.search 但没 return → output 捡回结果摘要并提示下次 return」。
那个机制靠的是**在沙盒侧识别"模型调过 web.search"**，
而我把它包成另一个函数之后识别不到了。

## 决定：回退，不改

回到 round 126 那版（只包顶层、无害、0 测试破），
然后把病因写进记录。

**没有往测试上打补丁**——那 7 个测试守着的是一个真机制
（"模型调了工具但没 return，要把结果摘要捡回来"），
为了让计数器工作去动它，顺序是反的。

## 下一轮正确的做法

不在 `createHostApi` 的出口包，而是**在工具实现里各加一行**：
`sendText` / `web.search` / `admin.*` … 每个函数入口出口各一次
`incrCounter('host_tool_calls_total', ...)`。

难看，但**它加在机制旁边，不是横跨在机制上面**。
round 126/127 的教训和 round 58 那个"第一版守卫是假的"是同族的：
**一个横跨整个表面的包装，比一个点上的改动危险得多。**

# 第一百二十八轮：找到了正确的插入点——但上下文不够做完

round 127 回退后，这轮去读那个被我横跨破坏的机制，
顺带找到了计数器**应该**加在哪。

## unviewed-results 机制（我从来没读过的一层）

`noteUnviewed(label, value)` 在**工具实现内部**被调，
记下"模型调了这个工具、可能没把结果 return 出去"：

  host-api.ts:497   computer.run(...)     → noteUnviewed(...)
  host-api.ts:531   computer.getText      → noteUnviewed(...)
  host-api.ts:2084  chats.find(q)         → noteUnviewed(...)

然后 `drainUnviewedResults()`（host-api.ts:2779）把积累的摘出来，
`executor.ts:252` 在每段结束时读它，把摘要拼进下一段的提示里。

**这就是那个测试守的东西**：「调了 web.search 但没 return →
output 捡回结果摘要并提示下次 return」。模型忘了 return，
机制替它把结果留在眼前。

## 为什么我的 Proxy 会破坏它

那个机制靠 `noteUnviewed` 在**原函数体内**执行。
我把 `web.search` 包成另一个 async 函数之后，
`await web.search(...)` 仍然会调到原函数、`noteUnviewed` 仍然会执行——
但沙盒侧的识别（它判断"模型调过这个工具"）看到的是**我的包装函数**，
对不上。

**一个横跨整个表面的包装，会让表面上每个挂钩都失焦。**

## 正确的插入点（已定位，未实施）

计数器该加在 `noteUnviewed` 的**调用点旁边**，而不是包住函数：

  host-api.ts:497   noteUnviewed(...)  ← 这里加 incrCounter
  host-api.ts:531   ← 这里
  host-api.ts:2084  ← 这里
  + 各工具的 logger.info('host sendText') 等既有日志点旁边

**"加在机制旁边"的意思是：和它共用同一个插入点，而不是横跨它。**

剩下的上下文不够我改完再跑全套门禁 + 部署 + 验证。
而 round 126/127 的教训正是**没验就推**——那这次不能再犯。
