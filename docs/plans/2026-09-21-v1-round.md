### 频率（用户投诉“日常过高”）

近 3 天 3,008 次群发送：小时窗 p50=6 / p90=26 / p99=63 / **max=107**；
5 分钟窗 p50=2 / p90=8 / **max=20**；最忙四群平均 14.7–19.4 条/小时。

两个病因，都是 bug 不是设计：

1. **发送预算每段归零**。executor 每段重建 `createHostApi`，`textSent` 归零，
   `maxTextSends=6` 其实是“每段 6 条 × 最多 10 段 = 60 条”。
   `semantic-dup.ts` 的注释早就写着“上限=6 —— 恰好就是 6，等于没拦”。
   证据：投递数分布恰好在 6 条处跳变（31 → 51），最差一个任务 46 秒 12 条。
2. **被叫到的回复一点间隔都没有**。最小间隔只拦主动发言，而生产流量几乎全在
   “被叫到”那条路上（2,702 次 `host sendText`：1,356 显式 `replyTo` + 1,340 只有任务默认锚点）。

另外：`TRENCH_BURST_MAX/ACTIVE` 原值 150/100 经 `envelope-backtest` 回测是**装饰性**的
（拦 0.0%）。已按实测改成 30/20（拦 11.9%，基本全是 p99 以上的失控小时）。

## 第二轮查出来的事实

### 视频（用户新指出）

"stepfun 模型实际上是可以视频 5min 以内输入的，vision 应该不止可以识别图片还可以识别视频"。

`multimodal.ts` 里只有一行 `[视频：用户发送了一段视频]` + "description not supported yet"。
**那个判断曾经是对的，现在过期了**——实测 step-5-preview 吃 base64 `video_url`，
6 秒测试视频准确描述了内容（彩色条纹/彩虹斜线/移动方块/左上角计时器）。

四个坑，三个是陷阱：

1. **不能蹭 vision 链**。同一个 `video_url` part 发给 step-3.7-flash 返回 **200 但
   content 为空**——token 全烧在 reasoning 上，`finish_reason=length`。
   "返回 200"不等于"看得懂"。所以加了 `AI_PROVIDER_X_VIDEO` 能力声明，
   smart-group 的 video profile 只收显式声明 true 的 label。
   方向性与 vision 相反是故意的：vision 没声明照发，video 没声明就不要。
2. **max_tokens 必须给够**（2000）。
3. **时长上限在下载之前判**（300s）。Telegram bot 下载上限 20MB（代码 10MB），
   5 分钟视频几乎必然超——现实里能描述的是短视频。
4. **绝不把 Telegram file URL 喂供应商**：那个 URL 里带着 bot token。

### 挖出的静默 bug（比功能本身重要）

全接完之后端到端跑出来是 **"我没看到你说的视频呀"**，而 prompt token 数也对得上。
原因在 `callModel`：`apiFormat === 'claude'` 时 content parts 被映射成
`p.type === 'text' ? p.text : ''` —— **图片、音频、视频全被换成空字符串**。
没有报错，token 数也对（只有文字那部分）。

修法：带媒体时绕过 claude 分支走 OpenAI 兼容裸路径（StepFun 的 `/step_plan/v1`
同时提供 `/messages` 和 `/chat/completions`，后者收 `video_url`；
Anthropic 原生 video block 在那个端点上回 400）。这条**顺带也修好了
claude-format label 的图片丢弃**。

### time gate（用户点名的"前置功能"）

TIMING_* 13 + TURN_* 17 个旗标，生产开 7 个。Meta 主路径**确实**跑 gate
（`src/meta/timing-adapter.ts` → `runTimingGate`）——我一开始猜"绕过
processPipeline 所以没跑"，看代码才纠正。

日志里它在真干活：333 no_action / 292 defer / 170 talk-value / 125 decision /
10 precheck / 620 dispatch gate suppressed。

**但 199 次 "gate parse failed"**（占 324 次的 61%）。env.ts 注释早就把这记成
"实测依据"放了很久。查下去发现 `rawSnippet` 全是空——不是解析不了，是**模型没输出**。

根因：调用点写死 `maxTokens: 200`，而 `.env` 把 `TIMING_GATE_USAGE` 设成
`reflection` → stepfun = step-3.7-flash（reasoning 模型，思维链计入 completion）。
实测同一 prompt：200 → content 空；800/2000 → 合法 JSON。
思维链吃光 200 token，JSON 没机会输出，然后 fail-closed 沉默——
**看起来像"gate 判了不说话"，实际是"gate 被截断了"**。
`labels.ts` 里 judge usage 的注释早就警告过这事，gate 是唯一还写死 200 的调用点。

已加 `TIMING_GATE_MAX_TOKENS`（默认 1200，实测合法 JSON 只需 ~260 token）。

### provider 池：33 个 label 只有 5 个成功过

`.env` 里 23 个 provider 指向 `http://127.0.0.1:3000/v1`，**那个端口上什么都没有**。

`tests/unit/core/loop/loop.test.ts` 里甚至有个测试叫

### ASI rubric：假度量

`reply_outcomes` 的 rubric 五列基本是常数：2070 行一模一样
(0.5,0.5,0.5,0.5,0.2,77.0)，只有约 20 行是真值。

① `maxTokens: 120`。judge → stepfun = step-3.7-flash（reasoning），

   **不吃 `response_format`**。StepFun 同一个 `/step_plan/v1` 也提供

**跟视频那条 bug 同源：一个只在一条代码路径上成立的能力。**
provider.ts 的注释早就写了"AI SDK generateText 不透传 reasoning_effort/thinking，
只有 raw 路径会把这些 body 字段发出去"——没人把它联想到 jsonMode 上。

改法：新增 `ASI_USAGE`（默认 'asi'）+ `ASI_RUBRIC_MAX_TOKENS`（1200），
.env 配一个同厂同模型、**不设 FORMAT** 的 label 让调用走裸路径；

# 第五轮：新增前置功能 + provider 池病因定位

## 新增前置功能：心流 LLM 失败时的保句闸

翻日志发现一个数字不对：`heart LLM failed, fail-closed pass` **1867 次**，
`Heart decision` 7443 次 —— **25% 的心流裁决是 LLM 调用失败**。

失败原因分解：
  1194  All labels exhausted（64%，整条 fallback 链死透）
   169  Content rejected
   162+32  timeout
    60  all accounts unavailable (cooling/disabled)
    56  ECONNRESET · 38 TLS 断 · 73 rate limited · 18 connect timeout

旧行为一律 `pass` = 消息被永久丢弃。对没人叫 bot 的群聊消息没毛病，但对**直接
叫到 bot** 的那句是另一回事：有人 @ 了本喵问一件事，因为线路故障，这句话就此
消失，对方永远等不到回复。这和"无视直接提问是另一种失败"是同一条原则，
只是失败方从模型变成了线路。

`HEART_LLM_FAIL_KEEP_ADDRESSED`（默认开）：LLM 判不了 + 被直接叫到 → `wait`
（走既有 wait-anchor 机制稍后重评），不 `pass`；没被叫到仍旧 `pass`（避免线路
故障时把整群闲聊都排成重试）。

wait 这条路两个消费方都已实现（heart.ts:313 和 meta/heart-adapter.ts:222），
所以保句是真保句，不是换个姿势丢弃。

## provider 池病因定位（比"端口写错"更具体）

"All labels exhausted" 占心流失败 64%，而它和 provider 池健康状况直接相关：
heart 走 judge usage → label `stepfun`，backups 里只有 `stepfunjudge` 健康，
其余 7 个是死 provider。**链的有效深度是 2。**

另外查到 `.env.example`（git 里的规范配置）明确写着本地 relay 是
`http://127.0.0.1:8317/v1`，而生产 `.env` 写的是 `3000` —— 这是**配置漂移**，
不是"未知上游"。但 model 名那一层仍然是决策（relay 217 个模型里约一半有对应、
一半没有，gpt-5.x / minimax / mimo / hy 全无），所以仍旧没有擅自重映射。

## provider 池：本地 relay 探不通，所以"改端口"不是解法

第五轮本来想给"23 个死 provider"找一个不需要人拍板的解法。线索是
`.env.example`（git 里的规范配置）明确写着本地 relay 是 `127.0.0.1:8317`，
而生产 `.env` 写 `3000` —— 看着像单纯的配置漂移。

**实测把这条线索否掉了。** 拿 relay 自己的 key 打它自己 catalog 里的 11 个候选模型：

| 模型 | 结果 |
|---|---|
| claude-sonnet-4.5 | HTTP 503 |
| claude-haiku-4.5 | HTTP 503 |
| grok-4-1-fast-reasoning | 45s 超时 |
| grok-4-0709 | 45s 超时 |
| grok-3 | 45s 超时 |
| kimi-k2.5 | HTTP 500 |
| glm-4.7-flash | HTTP 500 |
| glm-5 | HTTP 400 |
| qwen3.6-plus | HTTP 400 |
| deepseek-r1 | HTTP 400 |
| Gemini 3.1 Flash Lite Preview | 45s 超时 |

**11 个全挂。** 所以把 23 个 provider 改指 8317 只是把错误从
"connection refused" 换成 "503/400/500/超时"，一个都不会因此可用。
机器上**没有能用的本地 LLM relay**。

这反过来解释了心流失败的头号原因：heart 走 judge usage → `stepfun`，
backups 里只有 `stepfunjudge` 健康，其余 7 个是死 provider ——
**链的有效深度是 2**。两个 stepfun 都撞限流/超时时，"All labels exhausted"
（占心流失败 64%）就发生了。

结论：这不是配置能修的。bot 的实际可用池就是那 5 个健康的远程 provider
（stepfun / stepfunjudge / stepfunthink / stepfunvision / spark13），
要扩池只能加**远程** provider。这一步仍然要人决定加哪些。

# 第六轮：心流失败归因到链，再归因到账号

## 1. 头号失败原因不是超时限流，是思维链吃光 max_tokens

第五轮定位到"心流 LLM 失败占 25%，64% 是 All labels exhausted"。这轮往下挖一层，
看**每个 label 各自怎么失败的**：

  1481  stepfunthink     Empty response
   685  stepfunvision    Empty response
   583  stepfun          Empty response
   133  stepfunjudge     Empty response
   253  wbdsv41free      Empty response from SDK
   602  spark13          timeout
   …

**`Empty response` 2882 次，压倒性头号原因。**

根因：StepFun 那几个是 reasoning 模型，`reasoning_content` 计入 `max_tokens`。
思维链吃光额度时响应带 `stop_reason: 'max_tokens'` 回来，**一个 text block 都没有**。
`callClaude` 里有段注释说明这个现象，然后**故意**返回空字符串交给 fallback——
而 fallback 是同账号的另一个 label，撞同一个天花板，一次全灭。

先探针验"长 prompt + 4096 会不会空"——没复现。所以没继续猜，改成
**分开两种形状 + 把为什么空记进日志**：

  stop_reason=max_tokens + 无 text → 截断 → 加额重试一次（翻倍，上界 32k）
  stop_reason=end_turn  + 无 text → 模型真没话说 → 不重试

只对截断重试（审查/超时/限流重试只会翻倍延迟）。空正文时现在记
stopReason / blocks / outputTokens / maxTokens——此前 2882 次失败一点可诊断信息都没有。

## 2. 链的上游去重

同一个故障的另一面：健康 label 里四个共用同一个 endpoint + key，按延迟排序连排，
账号级限流一来四个同时死，链上瞬间一个不剩；真正独立的 step5 / spark13 被挤出名額。

`SMART_GROUP_DIVERSIFY_UPSTREAM`（默认开）：每个 (endpoint, apiKey) 只先取最快的
一个填前段，剩余名額才按分数补。5 名額的链开头从 2 个账号变成 3 个。

## 3. 一次断言修正（记下来是因为它是个真陷阱）

第一版测试断言"链里同账号 label 只出现一次"。错了——补位步骤会合法地把同账号的
加到尾部。真正该锁的性质是**前几个是不同上游**，不是"同账号只出现一次"。
写成后者会让一个正确的实现被测失败。

# 第八轮

## 1. scripts/session-report.mts
