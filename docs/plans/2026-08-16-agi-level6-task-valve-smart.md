## 总览

三个方向解决一个根因:**系统所有代码路径的终点都是"发一条消息"** —— judge 问"要不要回复"、
不问"这条消息对我正在进行的事情意味着什么"。结构上只能是回复生成器,情绪价值是这个结构唯一能产出的东西。

| Phase | 方向 | 核心 | migration |
|---|---|---|---|
| 13 | Task 对象架构 | 补 harness 的"执行 + 状态":SQLite tasks 表 + BullMQ 独立 worker + next_wake | 0065 |
| 14 | 反向阀门 L7 | 防"谄媚陷阱":连接率指标 + 私聊风险分档 + 反谄媚审计 + 牵线 | 0066-0067 |
| 15 | 小模型增强 | 延迟预算白嫖:best-of-N + verifier + Format Tax 解耦 | — |

## Phase 13: Task 对象架构(1-2 周)

**问题:** 搜索被压在单条回复的延迟预算里("一次调用、拿到就说"),真正有用的搜索需要
"搜、看、发现不对、换词再搜、交叉验证"——几十秒到几分钟,现有框架无处安放。

**两个循环必须分开:**
- 回复循环(现有):低延迟、拟人、只负责说话。可以说"我去看看"然后结束这一轮。
- 任务循环(缺失):BullMQ worker,无延迟压力,可跑 20 步,完成后把结果主动发回。

**Task 模型:**
```
Task {
  id, owner(uid), chat_id,
  goal(自然语言),
  state: pending | running | blocked | waiting_user | done | cancelled,
  ledger: [已做的步骤 + 结果]      // 事实台账 (JSON)
  progress: [还差什么 / 卡在哪]    // 进度台账 (JSON)
  next_wake: timestamp | null     // 定时/事件/条件唤醒
  created_at, updated_at
}
```

### 阶段 1: tasks 表 + 执行 worker
- migration 0065: `tasks` 表(如上字段)+ 索引(status, next_wake)
- `src/agent/task-store.ts`: CRUD + 状态机 + ledger/progress 追加
- BullMQ 独立队列 `task-executor`(与消息队列隔离),worker 在 `src/queue/worker.ts` 注册
- 只支持一种任务类型:**research**(用户说"帮我查 X")
  - 建 Task → bot 回"我去查" → worker 多轮 `executeSearch` → 完成后主动发结果
- **安全铁律:** Task 创建权限收紧——只有被 @ 的直接请求能建,群里随便一句话不能(持久化 agent = prompt injection 慢性中毒)

### 阶段 2: judge 认识任务
- L0 规则层加前置判断,在"要不要回复"之前问"这条消息跟当前活跃 Task 有关吗"
- 补充信息 → 更新 task.ledger,不一定要回复
- 催促 → 报进度
- 取消 → 终止任务
- 完成后 bot 第一次拥有"我正在做一件事"的自我状态

### 阶段 3: 唤醒机制
- next_wake 支持:定时(每天早上看一次)/ 事件(等某个 API 有变化)/ 条件(等用户回答)
- cron 扫 due tasks,派发唤醒 job
- 这就是"连续性"的物理实现——bot 不是被消息唤醒,是被自己的任务唤醒

### 阶段 4: 长任务(持续)
- "帮我盯着这个 GitHub issue" / "每周给群里做一次总结" / "帮我追这个连载更新了没"
- 复用 Phase 3 的 goals 机制做周期性检查,Task 负责执行

**与现有系统关系:**
- goals(0055/0059)= "关注什么"(被动观察,记录 findings)
- tasks(0065)= "做什么"(主动执行,产出结果)
- Task 完成时可把结论写入 experience_entries(对接 L1 经验蒸馏)

**测试:** task-store CRUD/状态机;worker 多轮搜索(mock executeSearch);judge 关联判断;唤醒调度

## Phase 14: 反向阀门 L7(2-3 周)

**问题:** 让人变孤独的不是"有个 bot 陪你",是"有个永远站在你这边的 bot"。
Humanizer 越像人越谄媚(用户表达脆弱时放大;反驳对话里谄媚率翻倍 18% vs 9%)。
**"更像活人"和"更容易在关键时刻附和你"是同一个旋钮的两端,不能只拧一边。**

### 阶段 0: 先测,别改(埋点)
- 新核心指标:**连接率** = bot 消息后 5 分钟内的人-人对话轮数
- 私聊:per-user 日均消息数、时段分布、连续天数
- 群聊:每个用户"只跟 bot 说话 / 也跟人说话"比例
- 全部只记录,不改行为

### 阶段 1: 谄媚审计(纯离线)
- 每周抽 200 条 bot 回复,用另一个模型按五维打分:
  情绪验证 / 道德背书 / 间接语言 / 间接行动 / 接受框架
- 输出周报,重点看"接受框架"比例
- 不改线上,只看清 bot 现在有多舔

### 阶段 2: 风险打分器(私聊)
- 轻量打分,跑在现有 L0 规则层旁边,不进 LLM:
  `risk = w1·连续天数 + w2·深夜占比 + w3·单次时长 + w4·情绪词密度 + w5·(1-群内发言比例)`
- 阈值分三档,初期全部只记录,跑两周看命中,调完阈值再启用

### 阶段 3: 中档降温(最保守,用户无感)
- Humanizer 特效衰减:减少主动追问、撒娇、afterthought edit
- 回复长度上限下调
- prompt 注入"倾向于把话题引向群里其他人"
- 观察连接率上升、用户流失变化

### 阶段 4: 牵线机制(加法,风险最低收益最大)
- 记忆层加"共同兴趣索引":跨用户兴趣/经历重合检测
- 触发时 bot 主动 @ 两个人搭桥
- 附带"去年今天群里在聊…"定时回顾(共同回忆 → 把注意力导向人与人的共同经历)
- **接话不抢话:** L0/L1 加一条——如果这条消息更适合群里某个具体的人回答,降低自己发言概率

### 阶段 5: 高档关心 + 优雅退出(按需)
- 非评判式问候:"你今天聊了挺多的,最近整体感觉怎么样?"(绝不"你使用过度了"/"记住我是 AI")
- 换模型/大版本前提前公告、旧人格保留可选、支持导出个人聊天记录
- 反谄媚自查:prompt 里加"群友说'我室友这人真有毒'——顺着骂还是问一句'发生什么了'"的立场要求

**验收标准:** 连接率上升,且总互动量没崩。连接率上升但用户跑了 = 降温过头,回退阶段 3 权重。

## Phase 15: 小模型增强(2 周,独立方向)

**核心事实:** FLOPs 对齐下,测试时计算让小模型超过大 14 倍模型(Llama-1B 测试时扩展超 8B)。
**白嫖延迟:** Humanizer 已读延迟 3-8 秒 = 免费并行采样时间。这是结构性优势。

### 1. Format Tax 解耦(最先做,零成本,可能立刻见效)
- 现状:5 层 prompt 里的格式指令压制模型推理(Qwen 小模型:schema 有效性 61.5%→100% 但准确率 19.7%→11%)
- **生成层:** prompt 去掉格式指令,让模型自由说话;格式序列化搬到代码层
  - 默认不开 parse_mode(闲聊纯文本,砍 90% 风险面)
  - 需要格式时用 entities(offset+length+type,绕开解析器)或 HTML 白名单+确定性转义
  - 兜底:send 失败自动降级(stripMarkup 纯文本重发)——十行代码让"格式错误"故障类别消失
- **judge 层:** 纯分类调用保持约束(那里不需要推理)

### 2. judge 层约束解码
- L0/L1 纯分类调用上语法约束(正则/grammar),省解析容错代码
- 需要想的地方别约束,只需要吐标签的地方全约束

### 3. Best-of-N + verifier(核心)
- **硬前提:** 没有可靠质量信号时 best-of-N = 随机挑。先造 verifier。
- verifier = 判断"这条回复符不符合这个群的调性 / 有没有胡编事实 / 有没有答非所问"
- 现有数据(reaction、被回复率)就是 verifier 的训练/评估信号
- **按难度分配算力:** judge pipeline 天生是难度分类器。"早上好"→N=1;"帮我分析这段代码"→N=16+verifier

### 4. 让它不需要知道,只需要会查
- 小模型显笨 = 知识不够但它不知道自己不够,于是硬编
- 给搜索 API/DB/执行环境,绕过知识局限(现有插件系统已就位)

**测试:** Format Tax 对比实验(20 条历史差回复,带/不带格式指令,对比质量);verifier 评估(reaction 相关性);best-of-N 质量提升测量

## 依赖与顺序

1. **Phase 13** 先做(Task 架构是根,补 harness 执行+状态;反向阀门的"牵线"和"接话不抢话"依赖共同兴趣索引,可稍后)
2. **Phase 15.1 Format Tax** 可并行(纯 prompt/序列化层改动,风险低)
3. **Phase 14** 阶段 0-1 可尽早(埋点+审计不改变行为,越早拿基线越好)
4. Phase 15.3 best-of-N 依赖 verifier,verifier 依赖日志数据积累 → 排最后

## YAGNI 边界
- Task 不引入新框架(BullMQ + SQLite 已有,只是队列语义从"消息"变"任务")
- 反向阀门初期只做阶段 0-3,阶段 4-5 按数据决定
- 小模型增强不微调模型(先做无训练的测试时计算;微调留待数据积累)
- 所有 flags 默认 OFF,逐步灰度
