# Objective status — 这个 goal 的结论

`known-issues.md` 是"还没解决的"，这张是"结论是什么"。两条合起来 = 完整答卷。

## 你的四个抱怨

### ① bot 很难融入话题

**诊断（四层可量的账，不是猜的）**：

| 层 | 数字 | 工具 |
|---|---|---|
| 话发出去没有 | 33% 曾被自己的闸咽回 → 现在 4% | `measure:voice` ⑤ |
| 发出后有人接没有 | self-act 5 条内 9%（慢热口径）/ 30 秒内 51% | `measure:engage` |
| 接得多快 | 两段 16.6s + 19.5s，p90 42s | `measure:timing` |
| 接的方式 | react 占 15.1%（6 种 emoji） | `measure:voice` ② |

**结论**：不是"没人理"，是**延迟**——它的话最终 89% 有人接，但一半要等
30 秒以上，那时话题常已翻篇。

**已做**：trench 闸被叫间隔 30s→8s、同一次 sendText 只过一次闸、
403 限流冷却 60s→300s、心流 LLM 失败 14% 拆出来可见。

**待你拍板**：群聊回复走快路径（预期 30s 快接 51% → ~80%）。
代价：那 30-60s 有时真在查东西。

### ② 前言不搭后语

**已修**：心流 why 脏 JSON 清洗（9%→0%）；同一锚点被回多次的闸。
**产品抽样**：94 条有锚回复全部对得上。

### ③ 重复回复概率太高

**已修**：四个闸（同任务内 / 同文本 30s / 跨任务 3 分钟 / 发送后记账）。
**证据**：四个闸现在每一个都有生产证据（`npm run gate:evidence`）：

| 闸 | 证据 |
|---|---|
| 重复锚点 | 拦住 2 次（同锚点重发同一句，round 131） |
| 代发目标不在群 | 拦住 13 次（round 86 首次验证） |
| 人在纠正止损 | 触发 1 次 |
| 同群同文本去重 | 0 次（判据场景还没出现） |

**过程中的两次自我修正**：
- round 123 我说"闸正确地没拦"是错的——被拦的尝试 msg 名不同，
  我的统计看不见它。**闸自己的日志是它动作的唯一观测点。**
- round 132 查出同一次发送标两遍账（telegram 出口 + host-api 批量），
  闸比设计早一轮拦。已修，生产验证：部署后 0 个双签（4655 个 key 扫过）。

### ④ 架构问题比上一个多太多

**已修**（都验过）：`closeRedis` 挂死（45 次强杀→0）、
403 循环（570 次 → 限流冷却 5 分钟）、5 处"只有 debug 日志的守卫"、
`--since` 藏了 42 轮的 `padStart` bug。

## 一分钟复述

> 它的话现在能出去，出去后有人接，但接得慢。已把让它变慢的闸和限流
> 都修了，剩一个要不要走快路径的选择。
