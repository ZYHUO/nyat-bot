The difference

Silence is a decision, not a failure.

A responding bot treats every message as a prompt. That's why group bots feel like vending machines. NyatBot's core loop decides whether to speak at all before it decides what to say — and it's the same self making both calls, with a first-person body state it can read.

What's actually built

Not a chat wrapper.

1 call
heart decision, not three filters

One persona-aware call decides reply / wait / pass, replacing the usual rule→micro→full filter stack. Mood, focus and social state go in; the verdict comes from the same self that will write the reply.

Host-side
the body it can't lie about

Nyat Trench: pressure, envelope and reflexes live in the host, where the model can read them but not change them. It learns the shape of its own throat from measurement, not from self-report.

Turns
bursts as one thought

Three messages in four seconds are one utterance. Interrupts mid-generation trigger a genuine replan; "wait for them to finish" actually resumes instead of dropping the thread.

Anti-ad
behavioural, owner-opted

Classic keyword matching finds nothing in this ecosystem — the noise is behaviour: burst, no-engagement, repeated payloads. A group owner turns it on by asking; the bot verifies they're really an admin before it listens.

Local
embeddings that don't phone home

Semantic memory runs on ONNX models cached on disk — no embedding API, no per-message cost, no third party reading your group's history.

Measured
not self-certified

Spot-the-bot harnesses, offline replay over real history, reaction-driven bandits. Nothing counts as working because the model said so.

How a message travels

From a phone in a group chat to a reply that sounds like a person.

   ▼

   │                                                                    host APIs: telegram / memory / stickers
   ├── L2 ──► heart ══► reply · wait · pass                     │
   │                    │                     │                            ▼
   │                    └─ pass ─────────────┴──── (silence, logged)   reply writer ══► segments ══► typing delay ══► send
   │
   └── Nyat Trench (host-held, model-readable):
        pressure P · burst envelope · refractory · directed debt
        ── every one of these is a number the model sees and cannot edit

The whole path is observable: logs/app.log is JSON lines, and /metrics exposes per-tool, per-label and per-outcome counters, so you can answer "how often does it choose silence, and was that the right call" with a query.

Extend it

A skill is a JSON file.

No SDK to install, no class hierarchy. Drop a JSON file in skills/ and the bot gains a tool it can decide to call — with an allowlist so a skill can't quietly become an open proxy. 

// skills/IP_QUALITY.json — a real, working example
{
  "name": "IP_QUALITY",
  "description": "Check whether an IP address is a known proxy/VPN exit. Use when someone asks about an IP.",
  "parameters": {
    "ip": { "type": "string", "description": "IPv4 or IPv6 address", "required": true }
  },
  "trusted": true,
  "execute": {
    "type": "http",
    "method": "GET",
    "url": "https://ipquality.example/api/{{ip}}",
    "allowedHosts": ["ipquality.example"]
  }
}

What the loader gives you for free

Schemaparameters are validated with zod before the model ever sees them — bad input becomes a tool error, not a hallucinated argument
Allowlisttrusted skills must declare a non-empty allowedHosts; the host refuses to even load them otherwise
No scripts"type":"script" is rejected at load time — the skill surface is HTTP-only by design, so a community skill can't run code
Namespace safetynames must match /^[A-Z0-9_]+$/ and can't shadow a built-in tool
Hot reloadfiles are re-read on preloadSkills(); no restart, no redeploy

Want to write one? Start from docs/skills.md — it has a complete walkthrough including the failure modes the loader guards against.

Run it

Thirty seconds to a running bot.

# clone, install, build
git clone https://github.com/ZYHUO/nyat-bot.git && cd nyat-bot
npm install && npm run build

# one file to edit
cp .env.example .env
#   BOT_TOKEN=…           ← from @BotFather
#   AI_PROVIDER_* / AI_USAGE_*  ← any OpenAI-compatible endpoint

npm start

Semantic memory needs Qdrant and local ONNX weights — both are fetched and verified by scripts/fetch-embed-model.mts, and the app degrades gracefully (and logs loudly) if they're missing. The full install script handles optional native acceleration. See the README for every optional piece.

Or just talk to the one that's already running

The production instance lives in group chats as @hunhemi_bot. It's a real catgirl with sharp edges — it will decline to answer things it thinks are beneath it, and it holds grudges. Don't poke it to see if it works; talk to it.

Design stance

The parts that are deliberately unusual.

Participationper-chat cognition turns, burst merging, interrupt→replan, wait→genuine resume. Silence is a logged outcome with a reason.
No servilitysycophancy is a structural RLHF artifact, not a tone bug. The persona has flaws and favourites; the human has top interrupt rights but is not a master.
Telegram as sensormentions and reply chains are addressee signals, reactions are unsupervised reward, topic ids are floor state. Not decoration.
Host-held bodypressure, envelope, refractory and debt are host-side numbers the model reads but cannot rewrite. What it knows about its own state is what it can't fake.
Verifiableoffline replay over real history, spot-the-bot harnesses, reaction bandits. A green test is a claim; an artifact is evidence.
Honest answers

What people ask first.

Every number below comes from the repo or the production log, and the uncomfortable ones are included. A project that only quotes its wins is telling you how it will behave as a dependency.

Is it accurate?

No guarantee, and the log says so. Over one production day the heart chose reply 44% / pass 55% — and 694 of those were heart LLM failed, fail-closed pass: the provider errored and the host swallowed the reply rather than guessing. That is the design (silence beats a wrong answer), but it means "it said nothing" and "it chose not to speak" are different things in the metrics, and the repo does not currently separate them for you.

Does it run on my machine?

Node 22 + Redis + SQLite. Qdrant and the ONNX embedding weights are optional — memory degrades and the app logs loudly instead of failing. No GPU, no Docker required (though deploy/ has systemd units).

Is it in production?

Yes. 24 groups hit it today, 10 with real volume, and it sent 1062 replies across the day. That is also where every number on this page comes from — including the ones above.

Where does my group's data go?

Qdrant runs locally. Embeddings are local ONNX models, so nothing leaves the machine for retrieval. The LLM calls obviously do go out — which is why the provider pool is configurable per-usage, and why a dead provider is a latency problem instead of a privacy one.

Why is it one 165k-line repo?

The two reusable engines moved out to packages/ (@nyat/nyatdb + @nyat/context-engine). The cognition layer stayed in the host because it is not reusable yet — it is entangled with this one bot's persona and timing. Splitting it earlier would have produced two repos that both need changing for every behaviour fix.

What is it bad at?

· Provider censorship. On Chinese providers a normal group chat can trip a content filter — one day saw 22 rejections that all traced back to one lively group, not to anything objectionable.
· Silent failures look like silence. See the accuracy answer.
· Setup is not one command. Bot token, AI keys, Redis, and (optionally) Qdrant. The install script handles the pieces; it cannot handle @BotFather.
